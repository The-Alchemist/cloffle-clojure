# Compile-Free Truffle Migration Plan for Cloffle

**Goal**: Make evaluation compile-free by default: no runtime JVM class generation for normal guest execution paths, while preserving practical Clojure semantics.

**Constraint**: Optimize for fast, testable progress — incremental milestones, not big-bang rewrite.

**Scope exclusion**: deftype, defrecord, defprotocol, reify (per requirements).

---

## 1. Current Architecture & Leak Points

### Pipeline Today
```
Source → LispReader.read() → [hostEval for HOST_EVAL_FORMS] → Compiler.analyze() → Expr → ExprToNode → Truffle nodes
```

### Class Generation Leak Points (excluding deftype/reify/defprotocol)

| Location | Trigger | Effect |
|----------|---------|--------|
| **FnExpr.parse()** | Every `(fn [...] body)` analyzed | Calls `fn.compile()` → `getCompiledClass()` → `loader.defineClass()` |
| **hostEval()** | `defmacro`, `require`, `ns`, `import`, etc. | Full `Compiler.eval()` → analyze + bytecode for any nested forms |
| **Compiler.bindings** | LOADER, RT.makeClassLoader() | DynamicClassLoader created and used |

### Key Insight
`ExprToNode.convertFn(FnExpr)` only uses `fnExpr.methods()`, `FnMethod` argLocals/body/reqParms — the **analyzed structure**, not the compiled class. The bytecode generated by `FnExpr.compile()` is never used when executing via Truffle. The class is only needed for `emit()` / `eval()` paths.

## 2. Architecture Options

### Option A: Compiler.analyze Split — "Lazy FnExpr" (Recommended First Step)
**Idea**: Add an analyze-only path that produces `Expr` trees without generating bytecode for `fn`.

- **Mechanism**: Introduce `Compiler.C.ANALYZE_ONLY` (or similar) and have `FnExpr.parse()` skip `fn.compile()` when in that mode. ExprToNode continues to consume `Expr` as today.
- **Tradeoffs**:
  - ✅ Minimal change: single Compiler branch, ExprToNode unchanged
  - ✅ Same macro expansion (Compiler.macroexpand1), same special-form handling
  - ⚠️ Requires patching upstream Compiler (FnExpr, possibly ObjExpr for future work)
  - ⚠️ Still dependent on Compiler internals (Expr layout, parser registration)

### Option B: Truffle-Native Analyzer Frontend
**Idea**: New analyzer that produces a Truffle-specific AST (not `Compiler.Expr`), with its own macro expander.

- **Mechanism**: Reader → macroexpand (reuse or reimplement) → custom AST (e.g. `CloffleAST`) → direct Truffle node generation. No `Compiler.analyze()`.
- **Tradeoffs**:
  - ✅ Full independence from Compiler side effects
  - ✅ Clear host-eval boundary (macro expansion can call host eval explicitly)
  - ❌ High effort: must reimplement/replicate special-form parsing, macro lookup, hygiene
  - ❌ Risk of semantic drift from Clojure

### Option C: Hybrid — Analyze-Only + Host-Eval Boundary Hardening
**Idea**: Combine A with explicit, narrow host-eval boundaries and compatibility tiers.

- **Mechanism**:
  1. Implement Option A (lazy FnExpr) for immediate compile-free `fn`
  2. Document and enforce: only specific forms (defmacro, ns, require, …) go to hostEval
  3. Add `*compile-free-mode*` (or similar) to gate behavior and fail fast on unsupported forms
- **Tradeoffs**:
  - ✅ Fast progress (A is small), clear compatibility story
  - ✅ Foundation for later B if desired
  - ⚠️ Still uses Compiler for macro expansion and special forms

**Recommendation**: Start with **Option C** — implement A, harden boundaries, add compatibility tiers. Defer B until A proves insufficient.

## 3. Minimal Viable Compile-Free Subset

Define **Tier 1** (compile-free, no class generation in guest path):

| Feature | Status | Notes |
|---------|--------|-------|
| Literals | ✅ | Already no class gen |
| `let`, `loop`/`recur` | ✅ | Already no class gen |
| `if`, `do`, `case` | ✅ | Already no class gen |
| `fn` | 🔧 | Requires lazy FnExpr (Option A) |
| `def` | ✅ | Var registration only |
| Invoke (non-protocol) | ✅ | Via InvokeNode |
| Map, vector, set, list literals | ✅ | Already no class gen |
| `try`/`catch`/`throw` | ✅ | Already no class gen |
| Java interop (`new`, `.method`, static) | ✅ | Uses reflection/existing classes |
| Macros (use) | ✅ | Expansion via host; macro *definition* is host-eval |
| `defmacro` | Host-eval | Defines macro Var; macro fn is compiled once on host |

**Tier 2** (constrained — may use host-eval or limited support):

| Feature | Strategy |
|---------|----------|
| `require`, `use`, `ns`, `import` | Host-eval only; document as boundary |
| `defmulti`, `defmethod` | Host-eval; multimethods stored in Vars, dispatch in guest |
| Qualified method calls | Already uses `buildThunk` → FnExpr; needs same lazy treatment as fn |

**Excluded** (per constraints): deftype, defrecord, defprotocol, reify.

## 4. Incremental Milestones & Test Gates

### Milestone 1: Lazy FnExpr (Compile-Free `fn`)
**Scope**: `FnExpr.parse()` skips `fn.compile()` when a "Truffle/analyze-only" mode is active.

- **Tasks**:
  1. Add `Compiler.C.ANALYZE_ONLY` or `*truffle-analyze*` dynamic var
  2. Gate `FnExpr.compile()` / `getCompiledClass()` on that flag
  3. Ensure `ExprToNode.convertFn()` never calls `compiledClass()` (it doesn’t today)
  4. Wire flag from `CloffleCompiler` and `Clojure.parse()` before `Compiler.analyze()`
- **Test gate**: `CloffleCompilerTest`, `CloffleReproTest`, `CloffleBehaviorTest` pass; no `defineClass` for `fn` (optional: assert via instrumentation or ClassLoader spy)

### Milestone 2: Host-Eval Boundary Hardening
**Scope**: Make host-eval explicit and fail fast on unsupported forms in compile-free mode.

- **Tasks**:
  1. Add `*compile-free-mode*` (or `*cloffle-compile-free*`) dynamic var
  2. When true, expand `HOST_EVAL_FORMS` with clear docs; reject or warn on forms that would require class gen
  3. Add `CompileFreeUnsupportedException` for explicit failures
  4. Ensure `eagerHostEvalInDo` and top-level host-eval preserve return values (already done)
- **Test gate**: New `CompileFreeBoundaryTest` — host-eval forms return correct values; unsupported forms fail with clear message

### Milestone 3: QualifiedMethodExpr / buildThunk
**Scope**: `QualifiedMethodExpr.buildThunk` returns `FnExpr`; those must also be lazy.

- **Tasks**:
  1. Confirm `buildThunk` produces `FnExpr` that would call `compile()` when `getCompiledClass()` is used
  2. With ANALYZE_ONLY, those FnExprs should never call `compile()`
  3. Add test: `(.method obj args)` in compile-free path
- **Test gate**: `JavaInteropTest`, `AdvancedFeaturesTest` pass in compile-free mode

### Milestone 4: Compatibility Tier Documentation & Toggling
**Scope**: Document tiers and allow toggling between "full" and "compile-free" modes.

- **Tasks**:
  1. Document Tier 1/2 in `CLOFFLE_NOTES.md` and this plan
  2. Add `CloffleContext` or env option for compile-free vs full
  3. Polyglot `Context` option: `"cloffle.CompileFree"` → true/false
- **Test gate**: CI runs both modes; compatibility suite passes in both

## 5. Risk Areas (defmacro, host-eval, context)

### defmacro
- **Risk**: Macro definition evaluates the macro body, which compiles a Clojure fn and stores it in a Var. That compilation generates a class.
- **Mitigation**: Accept that **macro definition** is host-eval and generates exactly one class per macro. **Macro use** (expansion) runs that fn — no new class. Document: "defmacro is a host-eval form; macro fns are compiled once."

### hostEval Boundaries
- **Risk**: `hostEval` calls `clojure.core/eval`, which can compile arbitrary code. Nested `fn` inside a host-eval form would generate classes.
- **Mitigation**:
  - Keep `HOST_EVAL_FORMS` as the sole entry points to hostEval
  - For `eagerHostEvalInDo`: only host-eval the listed forms; everything else stays in Truffle path
  - Consider: future "sandboxed" hostEval that runs with ANALYZE_ONLY when evaluating subforms (advanced)

### ClassLoader / Context
- **Risk**: `Compiler.LOADER`, TCCL, and `RT.makeClassLoader()` are wired for bytecode loading. In compile-free mode, we may not need a DynamicClassLoader for fn.
- **Mitigation**:
  - Keep LOADER bound (for ns/require/import and any residual host-eval)
  - In ANALYZE_ONLY, avoid `defineClass` for fn; loader still used for other host-eval forms

### defmulti / defmethod
- **Risk**: These are HOST_EVAL_FORMS. `defmethod` adds to a multimethod's dispatch table; the method fn can be a regular fn. If that fn is compiled during hostEval, we get a class.
- **Mitigation**: For Tier 1, treat as host-eval. Document. Tier 2 could explore storing method fns as Truffle callables if needed later.

## 6. Concrete First Implementation Steps

### Step 1: Add ANALYZE_ONLY Flag
**File**: `src/jvm/clojure/lang/Compiler.java`

Use a **dynamic Var** (not a new `C` value) so we can push it in Cloffle bindings without changing `analyze()` call sites:

```java
// Add near other Compiler Vars (~line 239), use Var.create for internal state:
public static final Var ANALYZE_ONLY = Var.create(Boolean.FALSE).setDynamic();
```

In `FnExpr.parse()`, replace the block at ~lines 4682–4694:

```java
try {
    fn.compile(fn.isVariadic() ? "clojure/lang/RestFn" : "clojure/lang/AFunction",
               (prims.size() == 0) ? null : prims.toArray(new String[prims.size()]),
               fn.onceOnly);
} catch (IOException e) {
    throw Util.sneakyThrow(e);
}
fn.getCompiledClass();
```

with:

```java
if (!Boolean.TRUE.equals(ANALYZE_ONLY.isBound() ? ANALYZE_ONLY.deref() : null)) {
    try {
        fn.compile(fn.isVariadic() ? "clojure/lang/RestFn" : "clojure/lang/AFunction",
                   (prims.size() == 0) ? null : prims.toArray(new String[prims.size()]),
                   fn.onceOnly);
    } catch (IOException e) {
        throw Util.sneakyThrow(e);
    }
    fn.getCompiledClass();
}
```

**Why Var**: `analyze()` is always invoked with `C.EVAL` or `C.EXPRESSION`. A Var lets Cloffle push `ANALYZE_ONLY → true` in its compiler bindings without modifying callers. `ExprToNode` never calls `compiledClass()` on `FnExpr`; only `emit()`/`eval()` do, which are not used on the Truffle path.

### Step 2: Wire Flag in Cloffle
**Files**: `CloffleCompiler.java`, `Clojure.java`

- In `pushCompilerBindings()` (or equivalent), add `Compiler.ANALYZE_ONLY` (or `*analyze-only*`) → `true`
- Ensure it’s pushed before `Compiler.analyze()` and popped after

### Step 3: Implement the Guard in FnExpr
**File**: `Compiler.java`

- Add `static final Var ANALYZE_ONLY = Var.create().setDynamic();` 
- In `FnExpr.parse()` before `fn.compile`:

```java
if (!RT.booleanCast(ANALYZE_ONLY.isBound() && ANALYZE_ONLY.deref() != null && ANALYZE_ONLY.deref()))
    fn.compile(...);
```

Or simpler: check `!Boolean.TRUE.equals(ANALYZE_ONLY.deref())` when bound.

### Step 4: Add Tests
**File**: `src/test/java/net/javacrumbs/cloffle/compiler/CompileFreeTest.java` (new)

- Test that `(fn [x] (+ x 1))` compiles and runs
- Test that `((fn [x y] (+ x y)) 2 3)` returns 5
- Optional: ClassLoader spy to assert no `defineClass` for fn classes (if feasible)

### Step 5: Update Documentation
**File**: `CLOFFLE_NOTES.md`

- Document ANALYZE_ONLY and compile-free path
- Add "Compile-Free Mode" section referencing this plan

- **Milestone 1**: All existing Cloffle tests pass; `fn` forms execute without `defineClass` for fn classes.
- **Milestone 2**: Host-eval forms have explicit boundaries; unsupported forms fail with clear errors.
- **Milestone 3**: Qualified method calls work in compile-free mode.
- **Milestone 4**: Tier documentation complete; compile-free can be enabled/disabled via option.
